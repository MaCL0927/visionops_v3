# M39.2 LEFT Robot Pose Transform

## Scope

M39.2 is an additive robot-pose layer on the M38.6.2 grasp geometry. It does
not change segmentation, RGB-D association, grasp selection, collision checks,
or the M38.6 Visual Grasp Frame definition.

The current production arm is **LEFT**. Startup is intentionally strict: a
calibration whose `robot_arm` is not `left` is rejected.

## Transform notation and chain

`T_A_B` maps coordinates in frame `B` into frame `A`.

```text
T_base_grasp
  = T_base_camera @ T_camera_grasp

T_base_hand_tcp
  = T_base_grasp @ T_grasp_hand_tcp

T_base_left_link7
  = T_base_hand_tcp @ T_hand_tcp_left_link7
```

The first matrix comes from M39.1. `T_camera_grasp` is the existing M38.6.2
`grasp_frame_camera.T_camera_grasp_rows`.

## M38.6 Visual Grasp -> LEFT hand_tcp

The installed-axis relationship already verified for the left hand is:

```text
M38.6 Grasp +X = hand_tcp +Z
M38.6 Grasp +Y = hand_tcp -Y
M38.6 Grasp +Z = hand_tcp +X
```

Therefore the rotational part of `T_grasp_hand_tcp` is known:

```text
R_grasp_hand_tcp =
[0,  0, 1]
[0, -1, 0]
[1,  0, 0]
```

However, the supplied M38.6.2 baseline and left-hand M39.1 calibration package
do **not** contain the exact translation between the M38.6 visual-grasp origin
and the designer `hand_tcp_link` origin. M39.2 therefore does not assume a zero
translation. The production configuration intentionally contains:

```yaml
visual_grasp_to_hand_tcp:
  enabled: false
  origin_policy: exact_transform_required_no_zero_translation_assumption
  T_grasp_hand_tcp_rows: null
```

With this safety gate, M39.2 immediately provides `T_base_grasp` and the base
pose of the M38.6 pregrasp/grasp frames, while `hand_tcp.available=false` until
an exact static 4x4 transform is supplied. When the exact matrix is available,
set `enabled: true` and fill `T_grasp_hand_tcp_rows`; the multiplication path is
already implemented and tested.

For pregrasp, M39.2 uses the existing
`candidate.pregrasp_center_camera_mm` directly and preserves the M38.6 grasp
rotation. It does not recompute pregrasp from a hard-coded distance.

## left_link7 / flange safety boundary

The supplied artifacts also do not contain the exact designer/URDF fixed
transform between `hand_tcp_link` and `left_link7`. Therefore
`hand_tcp_to_flange.enabled` is intentionally `false`.

M39.2 implements the flange multiplication path, but emits
`flange.available=false` until exact `T_hand_tcp_flange_rows` is configured. It
never substitutes the old M38 collision model's mounting-disk or wrist
approximation as a robot kinematic transform.

## Online output

For a M38.6 candidate with `grasp_frame_camera`, `/api/foam_ring/infer_once`
results include:

```text
robot_pose_transform_ready
robot_pose_transform.calibration
robot_pose_transform.grasp.T_camera_grasp_mm
robot_pose_transform.grasp.T_base_grasp_mm
robot_pose_transform.grasp.visual_grasp_pose_base
robot_pose_transform.pregrasp.T_camera_pregrasp_mm
robot_pose_transform.pregrasp.T_base_pregrasp_mm
robot_pose_transform.pregrasp.visual_grasp_pose_base
robot_pose_transform.hand_tcp
robot_pose_transform.flange
```

Current delivered configuration returns:

```text
status = base_grasp_ready
robot_pose_transform_ready = false
hand_tcp.available = false
flange.available = false
```

This is intentional: `camera -> base -> M38.6 Visual Grasp` is complete, while
robot TCP/flange execution remains gated until the two exact static tool
transforms are present.

If exact `T_grasp_hand_tcp` is configured, status becomes `ok` and these fields
also appear:

```text
robot_pose_transform.grasp.T_base_hand_tcp_mm
robot_pose_transform.grasp.hand_tcp_pose_base
robot_pose_transform.pregrasp.T_base_hand_tcp_mm
robot_pose_transform.pregrasp.hand_tcp_pose_base
```

If exact `T_hand_tcp_left_link7` is additionally configured, flange grasp and
pregrasp poses are produced as well.

`robot_ready` remains `false` in M39.2 because robot reachability, controller
trajectory validation, and the final robot communication/execution protocol are
outside this stage.
