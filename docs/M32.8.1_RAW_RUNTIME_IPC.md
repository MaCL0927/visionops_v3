# M32.8.1 Raw Runtime IPC 与延迟 JSON 解码

## 1. 背景

现场 A/B 测试表明，同一台 LB3576、同一 Runtime 与同一模型下：

```text
urllib       avg=62.08ms，约16.11 FPS
raw_socket   avg=36.86ms，约27.13 FPS
```

Runtime 服务端实际路由约 37–40 ms，urllib 路径额外增加了约 25 ms 固定延迟。M32.8 虽然已经拆分推理线程和后处理线程，但推理生产者仍使用 urllib 并在生产者线程中执行 JSON 解码，所以生产者吞吐仍受该路径限制。

## 2. 新链路

```text
推理生产者线程
  → TCP_NODELAY localhost raw HTTP
  → 一次 sendall 发送 HTTP header + `{}` body
  → 只读取原始 response bytes
  → latest-only result_queue

后处理线程
  → UTF-8 + json.loads
  → Runtime 结果校验
  → 洗衣液业务算法
  → 机器人消息与 Web 可视化
```

HTTP URL、请求体和 Runtime 返回协议均未改变。显式机器人 trigger 的可靠性保护继续沿用 M32.8。

## 3. 配置

```yaml
runtime_ipc:
  raw_http_enabled: true
  raw_http_fallback_urllib: true
  max_response_bytes: 33554432
```

- Runtime URL 为 localhost HTTP 时优先使用 raw socket。
- raw 请求失败时默认自动回退 urllib。
- 远程 Runtime 或 HTTPS URL 自动使用 urllib。

## 4. 状态指标

`GET /api/app/status` 的 `last_app_timing` 增加：

- `runtime_transport`
- `runtime_connect_ms`
- `runtime_send_ms`
- `runtime_headers_wait_ms`
- `runtime_body_read_ms`
- `runtime_server_queue_ms`
- `runtime_server_route_ms`
- `runtime_json_decode_ms`
- `runtime_response_bytes`
- `runtime_non_route_ms`

`pipeline.runtime_ipc` 提供累计 raw/urllib 请求数量、raw 失败次数和最后一次传输方式。

## 5. 预期

根据现场 A/B 结果，正式 App 的 `runtime_request_ms` 应由约 60–80 ms 降到约 36–42 ms。双线程流水线下，合理目标为：

```text
inference_stage_fps：约 24–27 FPS
detection_fps：约 22–26 FPS
```

单帧 `app_ms` 是端到端延迟，不必严格等于 `1000/FPS`。
