# M32.8.3 Orbbec USB 重连后 Web 快照冻结修复

## 现象

Orbbec 336L 拔出 USB 后重新连接，Bridge 的 `/stream.mjpeg` 已恢复实时画面，但 Collector 中的采集上传、模型验证和生产模式仍停留在断开前或重连后的第一张图。仅重启 Bridge 可能只刷新一张；在相机设置中保存配置会重启 Runtime，因此画面恢复。

## 根因

Orbbec Runtime 使用 POSIX RGB 共享内存推理，并允许 HTTP JPEG 回退。共享内存暂时不可用时，Runtime 会从 Bridge `/stream/snapshot.jpg` 读取 JPEG 并写入 `latest_jpeg_`。

共享内存恢复后，`latest_image_` 持续更新，但旧实现使用 `frame_is_fresh_locked()` 判断 `latest_jpeg_` 是否新鲜。该函数优先使用 `latest_image_.timestamp_ms`，因此已经停止更新的回退 JPEG 会借用实时 RGB 的时间戳，被永久判定为新鲜。`/api/runtime/snapshot.jpg` 随后一直返回这一张旧 JPEG。

## 修复

1. JPEG 缓存使用独立的 `latest_jpeg_timestamp_ms_` 判断新鲜度。
2. 对共享内存帧源，Runtime 快照优先直接代理 Bridge 当前 JPEG，而不是优先返回本地回退缓存。
3. 共享内存成功恢复后立即清空 HTTP 回退 JPEG 缓存。
4. 新增集成回归测试：先让 HTTP fallback 缓存 JPEG A，再恢复共享内存并把 Bridge 更新为 JPEG B，验证 Runtime 连续返回 JPEG B。

## 影响范围

仅修改 C++ Runtime 的快照缓存与共享内存恢复逻辑。Collector Raw HTTP、App 双线程流水线、机器人协议和 ROI 均未改变。
