# M36.2.1：Orbbec 共享内存访问权限与诊断修复

## 1. 故障现象

Bridge `/health` 显示 RGB/Depth 共享内存持续发布，但 Runtime 状态为：

```text
configured_transport = posix_shared_memory
transport = http_jpeg_fallback
shared_memory_sequence = 0
shared_memory_fallback_count 持续增长
```

当 Bridge 以 `root` systemd 服务运行，而 Runtime 由 `neardi` 启动时，旧 Bridge 创建：

```text
/dev/shm/visionops_orbbec336l_rgb  root:root 0660
```

`neardi` 无权执行 `shm_open(..., O_RDONLY)`，Runtime 因此每帧回退 HTTP。

缺少 `configs/runtime/generated/active_camera.json` 不是此次失败原因。读取模块在文件不存在时默认使用 `orbbec336l`，且 Runtime 状态已经证明配置源为 `shared_memory`。

## 2. 修改

- Bridge 新增 `VISIONOPS_ORBBEC336L_SHARED_MEMORY_MODE`，默认 `0664`。
- RGB 和 D2C Depth 共享内存统一应用该模式。
- Bridge `/health` 新增 `shared_memory_mode`。
- Runtime 状态新增 `frame_source.shared_memory_last_error`，HTTP 回退成功不再掩盖共享内存打开错误。
- 泡沫圆环 Runtime 启动脚本在启动前检查当前用户是否可读共享内存。
- M36.2 验收工具输出共享内存具体错误与权限提示。
- 新增 `diagnose_shared_rgb.sh`。

## 3. 临时验证

不重启 Bridge，先执行：

```bash
sudo chmod 0664 /dev/shm/visionops_orbbec336l_rgb
sudo chmod 0664 /dev/shm/visionops_orbbec336l_depth
```

Runtime 后台线程会继续重试，正常情况下无需重启便会切回：

```text
transport = posix_shared_memory
fallback_active = false
shared_memory_sequence 持续增加
decode_ms_latest = 0
```

该 chmod 在 Bridge 重建共享内存或服务重启后可能失效，只用于确认根因。

## 4. 永久修复

更新 Bridge 源码和 env：

```text
VISIONOPS_ORBBEC336L_SHARED_MEMORY_MODE=0664
```

重新安装或重编译 Bridge，随后重启：

```bash
cd /opt/visionops_v3/edge/camera_bridge/orbbec336l_bridge
sudo bash install_orbbec336l_bridge_service.sh
sudo systemctl restart visionops-orbbec336l-bridge.service
```

确认：

```bash
ls -l /dev/shm/visionops_orbbec336l_rgb
ls -l /dev/shm/visionops_orbbec336l_depth
curl -s http://127.0.0.1:18182/health | python3 -m json.tool
```

期望至少为 `-rw-rw-r--`，并且 `shared_memory_mode` 为 `664`。

## 5. 诊断

```bash
bash production/foam_ring_grasp/scripts/diagnose_shared_rgb.sh
```

然后重新运行 M36.2 验收。
