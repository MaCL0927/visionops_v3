# M32.8 洗衣液 inference/postprocess 双线程流水线

M32.8 将洗衣液 App 从单线程串行循环改为经过现场验证的两阶段流水线：

```text
inference producer
  └─ Runtime infer_once
       ↓ result_queue (capacity=1, latest-only for continuous frames)
postprocess worker
  └─ runtime validation + detergent algorithm + protocol/result build + WebSocket publish
```

当 CPU 后处理第 N 帧时，推理线程可以请求第 N+1 帧。吞吐由：

```text
max(Runtime inference stage, App postprocess stage)
```

主导，而不再近似等于两者相加。

## 触发可靠性

- 连续检测结果使用 latest-only 语义，队列满时允许覆盖旧连续帧。
- 显式机器人 trigger 带 `request_id`，不得为了连续帧而丢弃。
- trigger 到来时优先驱逐队列中的连续帧；如果队列中已有 trigger，则等待后处理线程消费。
- 连续结果超过 `max_result_age_ms` 会被丢弃，避免机器人和 Web 收到积压旧帧。

## 配置

```yaml
pipeline:
  enabled: true
  result_queue_size: 1
  max_result_age_ms: 500
```

`enabled: false` 可临时退回旧的串行路径，用于现场 A/B 验证。

## 状态

`/api/app/status` 新增：

```json
{
  "pipeline": {
    "enabled": true,
    "architecture": "inference_producer_latest_only_postprocess",
    "result_queue_size": 0,
    "result_queue_capacity": 1,
    "max_result_age_ms": 500,
    "inference_thread_alive": true,
    "postprocess_thread_alive": true
  },
  "counters": {
    "pipeline_results_dropped": 0,
    "pipeline_stale_results_dropped": 0,
    "pipeline_continuous_evicted_for_trigger": 0,
    "pipeline_continuous_dropped_for_trigger": 0,
    "pipeline_trigger_waits": 0
  }
}
```

少量 `pipeline_results_dropped` 对连续实时检测是正常的，表示 CPU 后处理暂时落后时保留最新帧。
任何 trigger 结果都不应出现主动丢弃计数。

## 预期

在 Runtime 约 32–38 ms、App 后处理约 10–25 ms 的情况下：

- 串行：约 12–17 FPS
- 双线程流水线：约 20–27 FPS

实际上限仍受 Runtime p95、机器人发送时间、CPU 调度和温度影响。
