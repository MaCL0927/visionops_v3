# VisionOps v3 M32.1：采集 ROI 第一阶段

## 1. 版本目标

M32.1 只实现 ROI 方案的第一阶段：**边缘端采集链路**。

本阶段完成：

1. 采集上传页新增“采集 ROI”按钮与矩形绘制窗口。
2. 手动拍照保存时，只保存 ROI 内的图像。
3. 定时采图复用同一保存函数，只保存 ROI 内的图像。
4. 浏览器“本地下载”同样下载裁剪后的图像。
5. 数据包携带独立的 `capture_manifest.json`。
6. 采集 ROI 与现有 Runtime 结果过滤 ROI 完全区分。
7. 一个采集批次只允许一套 ROI，避免训练数据混入不同坐标区域。

本阶段不修改：

- Camera Bridge 与共享内存取图链路；
- C++ RKNN Runtime 的模型输入；
- 服务端训练、模型导出和 `model.yaml` 生成逻辑；
- 生产推理性能；
- 已有 `/api/runtime/roi` 结果过滤逻辑。

## 2. 两类 ROI 的定义

| 类型 | 配置入口 | 作用 | 是否改变模型输入 |
|---|---|---|---|
| 采集 ROI | 采集上传页“采集 ROI” | 裁剪手动采集、定时采集、本地下载和数据包图片 | 当前阶段不改变生产模型输入 |
| 结果 ROI | 模型验证页“绘制 ROI” | Runtime 推理后按目标中心过滤输出 | 否 |

前端显示约定：

- 蓝色实线：采集 ROI；
- 黄色虚线：结果 ROI；
- 两套配置、接口和存储文件互不复用。

## 3. 采集数据流

```text
Runtime /api/runtime/snapshot.jpg
        ↓
Collector 获取一次 JPEG/PNG 快照
        ↓
读取 capture_roi.json
        ↓
ROI 关闭：原始字节直接落盘
ROI 开启：解码 → 像素裁剪 → JPEG/PNG 编码 → 落盘
        ↓
/opt/visionops_v3/data/images
        ↓
manifest.json + capture_manifest.json + images/
        ↓
.tar.gz 上传包
```

这里的裁剪只发生在低频采集路径，不参与生产推理，因此不会破坏已有共享内存、RGA 和 RKNN 性能优化。

## 4. 配置文件

默认路径：

```text
/opt/visionops_v3/data/capture_roi.json
```

覆盖变量：

```text
VISIONOPS_CAPTURE_ROI_CONFIG_FILE
```

配置示例：

```json
{
  "schema_version": "1.0",
  "message_type": "capture_roi_config",
  "enabled": true,
  "coordinate_space": "runtime_snapshot",
  "source_resolution": {
    "width": 1280,
    "height": 720
  },
  "normalized_xyxy": [
    0.328125,
    0.2083333333,
    0.890625,
    0.875
  ],
  "pixel_xyxy": [
    420,
    150,
    1140,
    630
  ],
  "crop_resolution": {
    "width": 720,
    "height": 480
  },
  "updated_at_ms": 1784900000000
}
```

坐标基于 Runtime 返回、Web 页面实际显示的原始快照：

```text
coordinate_space = runtime_snapshot
pixel_xyxy = [x1, y1, x2, y2]
```

其中右边界和下边界采用 Python/OpenCV 切片语义，不包含 `x2/y2`。

启用 ROI 时，宽和高都不能小于 32 像素。

## 5. API

### 5.1 读取采集 ROI

```text
GET /api/dataset/capture_roi
```

返回示例：

```json
{
  "schema_version": "1.0",
  "message_type": "capture_roi_state",
  "status": "ok",
  "capture_roi": {
    "enabled": true,
    "source_resolution": {"width": 1280, "height": 720},
    "normalized_xyxy": [0.328125, 0.2083333333, 0.890625, 0.875],
    "pixel_xyxy": [420, 150, 1140, 630],
    "crop_resolution": {"width": 720, "height": 480}
  },
  "image_count": 36,
  "batch_locked": true
}
```

### 5.2 保存采集 ROI

```text
POST /api/dataset/capture_roi
Content-Type: application/json
```

```json
{
  "enabled": true,
  "source_resolution": {"width": 1280, "height": 720},
  "normalized_xyxy": [0.328125, 0.2083333333, 0.890625, 0.875]
}
```

后端会把浏览器浮点坐标固化为源图像整数像素边界，再重新计算标准化坐标，避免每次采集出现一个像素的漂移。

### 5.3 关闭采集 ROI

```json
{
  "enabled": false,
  "source_resolution": {"width": 1280, "height": 720}
}
```

关闭后，后续采集保存完整快照。

### 5.4 批次锁定

采集目录存在图片时，如果新 ROI 与当前 ROI 不同，返回：

```text
HTTP 409
CAPTURE_ROI_BATCH_LOCKED
```

确认清空已有图片并切换：

```json
{
  "enabled": true,
  "source_resolution": {"width": 1280, "height": 720},
  "normalized_xyxy": [0.25, 0.20, 0.75, 0.80],
  "clear_existing_images": true
}
```

该请求会在同一个进程锁内完成：

```text
停止手动/定时写图竞争 → 删除已有图片 → 保存新 ROI
```

压缩包创建同样使用该锁，保证图片集合与 `capture_manifest.json` 一致。

## 6. 手动采集、定时采图和本地下载

### 手动采集

```text
POST /api/dataset/images/capture
```

保存结果增加：

```json
{
  "images_are_cropped": true,
  "capture_roi": {
    "pixel_xyxy": [420, 150, 1140, 630],
    "crop_resolution": {"width": 720, "height": 480}
  }
}
```

### 定时采图

定时任务仍调用 `save_runtime_snapshot()`，因此不需要独立实现 ROI 裁剪。修改 ROI、清空图片、打包和定时写图由同一 `_DATASET_LOCK` 协调。

### 本地下载

浏览器下载当前快照时使用同一归一化 ROI 做裁剪。它只影响用户直接下载的文件，不写入边缘端采集目录。

## 7. 采集压缩包

结构：

```text
<device>_<customer>_<timestamp>.tar.gz
├── manifest.json
├── capture_manifest.json
└── images/
    ├── visionops_*.jpg
    └── ...
```

`manifest.json` 新增 `capture` 段：

```json
{
  "capture": {
    "images_are_cropped": true,
    "manifest_file": "capture_manifest.json",
    "capture_roi": {
      "enabled": true,
      "source_resolution": {"width": 1280, "height": 720},
      "pixel_xyxy": [420, 150, 1140, 630],
      "crop_resolution": {"width": 720, "height": 480}
    }
  }
}
```

`capture_manifest.json` 是后续服务端第二阶段应读取和持久化的正式采集元数据。

## 8. 分辨率保护

启用 ROI 后，采集时的 Runtime 快照分辨率必须与绘制 ROI 时一致。

例如 ROI 是在 `1280×720` 图像上绘制，而当前快照变为 `640×480`，Collector 会拒绝裁剪，并提示重新绘制。M32.1 不会静默按比例缩放，因为宽高比或 Bridge 画面方向变化可能造成错误采集区域。

## 9. 部署与重启

覆盖代码后，重启实际承载 Collector Web 的任务级服务。洗衣液任务使用：

```bash
sudo systemctl restart visionops-v3-detergent-grasp-collector.service
sudo systemctl status visionops-v3-detergent-grasp-collector.service --no-pager
```

查看日志：

```bash
journalctl -u visionops-v3-detergent-grasp-collector.service -f -n 100
```

```text
/opt/visionops_v3/data/

```

## 10. 验证步骤

1. 打开“采集上传”页面，刷新快照。
2. 点击“采集 ROI”，拖动蓝色矩形并保存。
3. 手动拍一张图，确认采集列表中图片尺寸等于 ROI 尺寸。
4. 开启定时采图，确认后续图片尺寸一致。
5. 创建上传包，解压检查 `capture_manifest.json`。
6. 保留一张图片后尝试修改 ROI，应收到批次锁定提示。
7. 到模型验证页绘制黄色结果 ROI，确认不会改变采集 ROI。
8. 切换相机分辨率后采集，应提示重新绘制采集 ROI。

检查压缩包：

```bash
tar -tzf /opt/visionops_v3/data/upload_packages/<package>.tar.gz

tar -xOf /opt/visionops_v3/data/upload_packages/<package>.tar.gz \
  capture_manifest.json | python3 -m json.tool
```

## 12. 后续阶段接口约定

第二阶段服务端应读取：

```text
capture_manifest.json.capture_roi
```

并把它沿数据集、训练任务、导出模型传递到 `model.yaml`。第三阶段 Runtime 再读取模型包中的 `preprocess.input_roi`，通过 RGA 融合完成裁剪、缩放和颜色转换。

M32.1 不提前复用现有 `roi` 字段，避免把“采集裁剪”“模型输入裁剪”“结果过滤”三种语义混在一起。
