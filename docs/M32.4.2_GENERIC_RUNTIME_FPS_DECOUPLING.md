# M32.4.2 Generic Runtime 推理 FPS 解耦

## 问题

使用以下通用启动方式时：

```bash
bash scripts/start_runtime.sh
bash scripts/start_collector.sh
```

生产模式和模型验证由浏览器直接循环调用 Runtime：

```text
POST /api/runtime/infer_once
GET  /api/runtime/snapshot.jpg
```

旧实现把一次实时循环写成串行流程：

```text
infer_once
  ↓
snapshot.jpg
  ↓
JPEG 下载、浏览器解码、Canvas 绘制
  ↓
等待剩余周期
  ↓
下一次 infer_once
```

因此设置的 30 FPS 不只受模型推理耗时限制，还被 Web 快照刷新拖慢。即使 Runtime
`total_ms` 约 33 ms，只要快照下载和浏览器显示额外消耗约 140～150 ms，实际请求周期
就会达到约 180 ms，对应约 5.5 FPS。

旧生产页面又用整个 UI 循环耗时计算“推理 FPS”，所以显示值实际是“推理 + 画面刷新
FPS”，不是 Runtime 推理完成率。

## 修改

M32.4.2 将实时工作拆成两个互不等待的循环：

```text
推理循环（production_inference_fps）
POST /api/runtime/infer_once
  ↓
记录最新结果和真实推理完成率
  ↓
立即调度下一次推理

画面循环（display_fps）
GET /api/runtime/snapshot.jpg
  ↓
JPEG 解码和 Canvas 叠加
  ↓
按画面 FPS 刷新
```

推理循环不再等待 JPEG 快照。默认画面仍可保持 5 FPS，而 NPU 推理可接近模型和 HTTP
链路允许的最大值。

当单次 `infer_once` HTTP 往返已经接近或超过目标周期时，循环不会叠加多个并发推理请求，
而是在上一次完成后立即提交下一次。因此 33 ms Runtime + 少量 HTTP 开销的模型，30 FPS
设定下通常接近 27～30 FPS，而不会虚假显示为 30 FPS。

## FPS 显示

生产模式现在显示：

```text
实际推理 FPS / 设定推理 FPS · 画面 FPS
```

实际推理 FPS 使用最近 2 秒的 `infer_once` 完成时间滑动统计，不包含快照下载和图像绘制。
业务 App 模式仍优先使用 App 返回的 `producer.actual_fps`。

模型验证页新增：

- 推理 FPS / 设定
- 画面 FPS

## 配置持久化

`production_inference_fps` 现在写入：

```text
/opt/visionops_v3/configs/runtime/generated/vision_box_settings.json
```

因此通用 Runtime 模式不再只依赖当前浏览器的 localStorage。Collector 重启或更换浏览器后，
仍会读取同一套生产/验证推理 FPS。

`start_collector.sh` 明确支持：

```bash
VISIONOPS_PRODUCTION_INFERENCE_SOURCE=runtime bash scripts/start_collector.sh
```

默认值就是 `runtime`。绑定业务任务时可使用 `app`。

## 兼容性

- 不修改 C++ Runtime，不需要重新编译。
- 手动拍照检测和手动生产检测仍会同步刷新一次快照。
- `production_inference_source=app` 的后台生产者逻辑保持不变。
- 离开模型验证页时会停止隐藏的实时推理循环，避免后台继续占用 NPU。
